Two proof stacks

A proof system is only as sound as its implementation, so Siontology never trusts one. Proof stack A is the reference executor. Proof stack B is a second implementation of the state transition, written only from the specification. Every chunk of every Pulse goes through both, and a World Proof verifies only if both accept.

A script run in CI checks that stack B never calls the reference executor’s logic. Differential tests drive thousands of chunks, random workloads, boundary probes and tampered inputs through both stacks. They found two defects in the reference executor and several gaps in the specification, all fixed in version 1.1: a market clearing deadline near the largest 64-bit value overflowed when its batch sealed, which let any account halt the chain, and a charter window near the same value made the reference executor disagree with the specification.

Both stacks still share the hashing, Merkle, signature, Assurance Algebra and clearing-certificate code, so a bug there would be common to both. That shared code is named as a separate assumption, impl:shared-primitives, in the trust formula of every World Proof.

The specification

The state transition specification is normative: it defines the function a proof stack evaluates for every chunk of every Pulse, and through it the whole state transition, from preparing and executing one transaction to the three phases of a Pulse and the commitments each chunk statement carries. Where the two implementations disagree, one of them is wrong.

Since version 1.3 the state transition covers validators, stake, epochs and the response to censorship, so every committee change follows its rules and the World Proof covers it. Version 1.4 pays validators from fees alone; version 1.5 takes their seats from slashed validators even when nobody else is eligible. Later versions add what agents need from the ledger. It is at version 1.15, and both proof stacks implement it.

  1. v1.1

    From differential testing of stack B against stack A: saturating deadlines and windows, bounded market periods, specified deferred-phase errors, and what the World Proof binds.

  2. v1.2

    From independent reviews: transaction signatures bound to the chain, bounded inputs, allotments, batches, formula depth and certificate size.

  3. v1.3

    Staking with proof of key possession, unbonding, rewards by weight, slashing of equivocation with a share to the reporter, forced-inclusion obligations and committee rotation.

  4. v1.4

    Rewards from fees only: the state keeps a running total of fees collected, and each epoch pays its validators a share of what was collected during it, so slashed stake and other funds in the treasury never add to rewards.

  5. v1.5

    From an independent review: slashed validators lose their seats at the epoch boundary even if nobody else is eligible, so a chain whose every eligible validator was slashed halts instead of running on them.

  6. v1.6 to v1.15

    Among them: payment streams with checkpoints; agent identities, subagents and suspension; memory logs that can only grow; Task Charters; storage deals proven every round; one signature for a batch of keyless subagents; lineage ids and token buckets; verifiers a task names who must attest. The changelog has every version.

Contributing

The rules in AGENTS.md apply to everyone who changes the code, people and AI agents alike. Seven of them are not negotiable.

  1. One encoding

    Every consensus-critical value has one canonical Borsh encoding and is hashed with a domain tag.

  2. Deterministic order

    Consensus-critical maps are ordered maps; no hash-map iteration order may influence a hash, a root, an ordering or a decision.

  3. No floating point

    Money is fixed-point micro-units; exact optimisation uses rationals. Floats are for reporting only.

  4. Nothing is deleted

    Consumed objects are tombstoned and claims are appended, so history stays auditable and proofs stay stateless.

  5. Every assumption named

    Anything the system relies on that is not proven is an atom in some trust formula, including the implementation’s own shortcuts.

  6. Shortcuts labelled

    Simulation-only shortcuts, such as fast test signatures and replay proofs, are labelled in the types and never silently replace real cryptography.

  7. No unsafe Rust

    The workspace forbids it.

Seed every random number generator, write a property test for every algebraic or adversarial invariant, and document and test public functions. The suite includes property tests for the Assurance Algebra, the linear-programming certificates and the state machine, a deterministic consensus simulator with adversarial network phases, scenario tests for every transaction kind, end-to-end devnet tests with dual post-quantum signatures, the agent runtime against a scripted model and stand-ins for the services it talks to, and the demos.

Found a vulnerability? Report it privately, as the security page describes, not in a public issue.
