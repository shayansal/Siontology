Agents that cannot overspend

For
Companies that let AI agents spend money: on compute, data, API calls or goods, on someone’s behalf.
Today
An agent’s limits live in its own code, its prompt or a card’s settings, so a prompt injection, a bug or a stolen key can spend whatever the agent can reach. Gartner expects AI agents to intermediate 90% of B2B buying, more than 15 trillion USD, by 2028 (Gartner).
With Siontology
An Agent Charter is an object on the ledger that fixes whom the agent may pay, how much per payment and per window, its budget, and who answers for it. Validators check every payment against the charter before it executes.
What changes
The worst case is known before the agent starts: at most its budget, only to listed payees. A compromised agent is stopped by the ledger, not by its own judgement, and revoking the charter stops the agent and every sub-agent it created.
Status
Built on the devnet
Not built: limits on which models may act under a charter, and adapters for other agent-payment standards such as AP2 and ERC-8004.
  1. Charter

    The company creates a charter: payees, a limit per payment and per window, a budget, receipts on, and a bond behind the agent’s receipts.

  2. Pay

    The agent pays a listed payee within its limits. The payment executes and its receipt joins the knowledge log.

  3. Refuse

    A payment to an unlisted payee, or above a limit, is refused by the validators, whatever the agent was told.

  4. Delegate

    The agent can give a sub-agent part of its budget under narrower limits, never wider ones.

  5. Revoke

    One transaction revokes the charter. Once it executes, the agent and all its sub-agents are refused.

APIs paid per request

For
Anyone selling an API, a dataset or a model behind an HTTP endpoint, and the agents that buy from them.
Today
A card payment costs more than one API call is worth, so APIs are sold as monthly plans behind accounts, API keys and invoices. US merchants paid 198.25 billion USD in card fees in 2025 (Nilson data, via the Merchants Payments Coalition).
With Siontology
The API answers a request with HTTP 402 Payment Required and a quote. It speaks x402, the open standard for payments over HTTP, a Linux Foundation project, with two ways to pay. An agent that calls once pays in a stablecoin, under its charter if it has one, and the server checks the payment as a light client before it answers. An agent that calls often opens a payment stream to the API once, then pays each call with the next element of a hash chain, which the server checks with one hash; the server settles thousands or millions of calls in one transaction.
What changes
No accounts, keys or invoices. Every request is paid and checked before it is served, a replayed payment is refused, and an agent cannot pay more than its charter or its stream allows. With a stream, a call costs the server under a microsecond to check and the ledger about two nano-USD in fees, measured.
Status
Built on the devnet
x402 version 2 with the exact scheme and Siontology’s stream scheme, not yet tested against third-party x402 clients. Streams pay one API, one way, out of escrow the agent locks in advance.
  1. Ask

    The agent requests a resource. The server answers 402 with a quote: price, payee, chain and a fresh nonce.

  2. Pay

    The agent signs a payment whose purpose names the quote, and retries the request with it.

  3. Check

    The server submits the payment, waits for it to execute and verifies the receipt the way a light client would: committee certificate, certified order, inclusion proof.

  4. Serve

    Only then does the API answer 200 OK. The same payment cannot buy a second request.

For an agent that calls the same API often, a payment stream replaces the transaction per call:

  1. Open

    The agent escrows funds for the API and publishes the last element of a secret hash chain, once.

  2. Pay

    Each call carries the next element of the chain. The server checks it with one hash and serves at once; nothing goes to the ledger.

  3. Settle

    From time to time the server settles everything it has accepted in one transaction, proven by a checkpoint, for a fee that does not grow with the number of calls.

Receipts for AI output

For
AI providers that must mark what their models generate, and the platforms, newsrooms and courts that need to check it.
Today
The EU AI Act has required machine-readable marking of AI-generated content since 2 August 2026, and systems already on the market must comply by 2 December 2026 (timeline). A watermark inside the content can be stripped or imitated, and a provider’s own database vouches only for itself.
With Siontology
The provider issues a receipt for each output: a claim naming the model, the time and a hash of the content. Each receipt carries a formula of what it rests on, such as the provider’s signature, a hardware attestation and a bond.
What changes
Anyone can check a receipt against the ledger, and see what forging it would cost under their own assumptions, without trusting the provider’s database. The design target is under 0.0001 USD per receipt.
Status
Claims and their pricing built on the devnet
Not built: a receipt service that commits many outputs in one claim, and an SDK for providers. The cost per receipt has not been measured.
  1. Bond

    The provider posts a bond behind its receipts.

  2. Issue

    Each output gets a receipt whose formula is the provider’s signature and either a hardware attestation or the bond.

  3. Price

    A consumer computes the receipt’s cost of corruption under its own policy: whether it trusts the hardware, distrusts it, or prices an attack on it.

  4. Decide

    The consumer relies on the receipt only if that cost covers its value at risk, times a safety factor.

Payments a deepfake cannot approve

For
Finance and treasury teams, and anyone who moves large payments on instructions given by voice, video or email.
Today
US victims reported a record 20.9 billion USD in losses in 2025, 3.05 billion of it from business email compromise (FBI IC3). One deepfake video call cost the engineering firm Arup about 25.6 million USD (CNN).
With Siontology
The treasury’s payment agent works under a charter that requires evidence above a threshold: a mandate claim from the people or systems that must agree, each backed by a bond. The payment executes only if what the approvers would forfeit by lying exceeds the amount at risk.
What changes
Imitating a face or a voice is no longer enough. An attacker has to corrupt approvers whose bonds exceed the payment, and what they forfeit repays the loss.
Status
Partly built
Charters already refuse a payment above a threshold without a claim that passes the decision rule, and claims, bonds and slashing are built. The approval workflow and the apps around it are not.
  1. Set the rule

    The treasury charters its payment agent: above a threshold, a payment needs a claim that passes the decision rule.

  2. Request

    A payment request arrives by call or email, and the agent prepares the payment.

  3. Approve

    The approvers issue a mandate claim, each backed by a bond. Its formula names whose approval it rests on.

  4. Check

    Validators compute the claim’s cost of corruption. The payment executes only if it covers the amount times the safety factor.

  5. Repay

    If an approval is proven false, its bond is slashed and compensates the payer.

Invoices that repay you if they are false

For
Invoice financiers, trade-finance platforms and marketplaces that pay out before goods are confirmed.
Today
A financier that funds a false invoice recovers through insurers or the courts, if at all.
With Siontology
The supplier, the shipper and an arbiter each post a bond behind what they attest. The invoice is a claim whose formula names those attestations, so its cost of corruption is what a forger would have to forfeit. A financier relies on it only up to what that covers, reserves that much of the backing so nobody else can count on the same bonds, and is repaid from slashed bonds if a challenge proves the invoice false.
What changes
Reliance on a false invoice is repaid in full, a few Pulses after the ruling, without a lawsuit, from bonds posted in advance.
Status
Built on the devnet
Rulings come from an adjudicator named in each claim; there is no network of adjudicators yet.
  1. Bond

    The supplier bonds 30,000 USD behind its invoices, the shipper 20,000 USD behind its deliveries, and an arbiter 100,000 USD behind its rulings.

  2. Attest

    The shipper attests the delivery; the supplier issues the invoice for 10,000 USD, resting on its own bond or on the delivery.

  3. Price

    The invoice’s cost of corruption is 50,000 USD: a forger must corrupt both routes.

  4. Fund

    A financier relies on 10,000 USD with a safety factor of 2 and reserves 20,000 USD of the backing. A request to rely on 30,000 USD is refused.

  5. Repay

    The buyer challenges, the arbiter upholds, the bonds are slashed, and the financier is repaid 10,000 USD automatically.

Markets that prove their prices

For
Marketplaces for GPU compute, energy and other goods that clear many orders at once, and the buyers and sellers who use them.
Today
Matching engines are black boxes. Participants cannot check that the allocation was the best available, and when the order of arrival decides who trades, arriving first is worth money and gets gamed.
With Siontology
Orders are sealed into a batch with the Pulse’s random beacon, so nobody can reorder them. A solver computes the allocation that maximises total welfare and submits it with a certificate, its dual prices; the ledger checks the certificate in linear time and settles everyone at one price.
What changes
Every batch carries proof that no better allocation existed. A place in the batch is worth nothing, so there is nothing to front-run.
Status
Built on the devnet
Sealed double auctions and assignment markets. Convex and combinatorial markets are designs.

Settlement with compliance proven

For
Fintechs, remittance companies and payment providers that move stablecoins across borders.
Today
Sending 200 USD abroad costs 6.36% on average, and 14.99% through banks (World Bank, Q3 2025). Financial-crime compliance costs 206.1 billion USD a year (LexisNexis, 2023).
With Siontology
Stablecoin transfers settle on the ledger in seconds and stay private by default. KYC, Travel Rule and sanctions checks are proven with zero-knowledge proofs: the receiving institution learns that the checks passed, not the data behind them.
What changes
The design goal is a few cents per transfer, with compliance checked once, in a proof, instead of repeated by every intermediary.
Status
Not built
Stablecoin transfers run on the devnet with public amounts. Confidential amounts and compliance proofs need a zero-knowledge proof stack that is not built yet.

Provenance that survives a platform

For
Newsrooms, camera makers, creators and platforms that publish media with C2PA content credentials.
Today
Platforms strip content credentials on upload. In one Washington Post test, none of eight platforms kept an AI video’s credentials (report).
With Siontology
A media manifest is registered as a claim. When a platform strips the metadata, the claim is found again by the content’s hash, and a revoked manifest shows as revoked.
What changes
Provenance stops depending on every platform keeping metadata intact.
Status
Not built
A claim can carry a manifest’s hash today; the C2PA adapter and lookup by content hash are not built.
